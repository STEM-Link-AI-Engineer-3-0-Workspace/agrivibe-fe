Lesson 01 · 6 minData model

A thread is a conversation. A turn is one question and its answer.

Your win

Explain AgriVibe's data model in one sentence: a farmer has many threads, and a thread has many turns.

Nipuna put it well in the session: a thread is a continuous sequence of messages between the user and the assistant, more like a session. Click New chat in Claude or ChatGPT, say “hey”, and you've started one.

What happens inside a single question is richer than a message. The assistant may call tools, ask specialists, save requirements. AgriVibe bundles all of that into a turn: the question, the answer, the tools called, the requirements saved, each specialist's findings, and how long it took.

Domain model first, code second

Before any endpoint, Manu drew the entities. Two one-to-many relationships:

The same model in Pydantic

The shapes live in models/chat.py and models/threads.py, as Pydantic models1. Read them as a story:

agrivibe-be/src/agrivibe/models/view on GitHub ↗
class Turn(BaseModel):                 # one question and everything done to answer it
    message: str
    answer: str
    tools_called: list[str]
    requirements: dict[str, str] | None
    findings: dict[str, Finding]
    started_at: datetime
    seconds: float

class ChatResponse(Turn):              # what POST /chat returns: a turn + its thread
    thread_id: str

class ThreadSummary(BaseModel):        # one row in the sidebar
    thread_id: str
    title: str
    created_at: datetime
    updated_at: datetime
    turns: int

class Thread(ThreadSummary):           # the whole conversation
    history: list[Turn]
A mix-up from the session

“So Thread is the base class and Turn is a subclass?” No. Look at the parentheses: Thread extends ThreadSummary, and ChatResponse extends Turn. A thread contains turns, through history: list[Turn]. Containing is not inheriting.

Manu called Thread a projection: it isn't stored as one object. When you open a conversation, the backend reads the summary and the turns and assembles a Thread from them. So thread.history gives you turn 1, turn 2, … in order.

And ChatResponse is just a turn with a thread_id attached. That id is what links the turn to its conversation, and the conversation to the farmer.

Lesson 02 · 9 minPostgres · LangGraph · SQL

From memory that forgets to tables that keep their shape

Your win

Say what lives where in Postgres, and what each rule in AgriVibe's tables protects you from.

Remember restarting fastapi dev and losing every conversation? The threads lived in memory, inside the running process. When the process stopped, they were gone. The fix is to persist them somewhere that outlives the process: Postgres. It happened in two steps.

Step 1 · LangGraph's own storage

LangGraph gives you two pieces that know how to save themselves1:

PieceKeepsKeyed by
CheckpointerThe graph's state at every step of a run: messages, tool calls, findings. A checkpoint is one of those snapshots. It's how a conversation continues.thread_id
StoreLong-term key–value data the agents choose to save across threads. In AgriVibe: what the orchestrator remembers about the farmer, such as their field.a namespace + a key

Neither is created inside the agents. They're injected at startup, so swapping the in-memory versions for Postgres ones changed no agent code. Everything shares one connection pool:

    await app.state.thread_service.add_farmer(Farmer(id=settings.farmer_id, ...))  # the seed

# core/database.py: what open_database hands over

Each request then picks up the shared service through FastAPI's Depends2, and tests swap it with dependency_overrides3.

Step 2 · AgriVibe's own tables

In the session, threads and turns were also saved in LangGraph's store: JSON under text keys like threads.frm_7f3a9c2e. Manu called it flat, with normalising to come. The trouble with flat: the model from lesson 01 existed only in those strings. Postgres couldn't check a thread's owner, join a thread to its turns, or delete them together.

So the backend now owns three tables, written in plain SQL with no ORM. They're exactly the diagram from lesson 01:

agrivibe-be/src/agrivibe/core/schema.sql (trimmed)view on GitHub ↗
CREATE TABLE farmers (
    id    text PRIMARY KEY,
    name  text NOT NULL
);
CREATE TABLE threads (
    id         uuid PRIMARY KEY,
    farmer_id  text NOT NULL REFERENCES farmers (id) ON DELETE CASCADE,
    title      text, created_at timestamptz, updated_at timestamptz
);
CREATE INDEX threads_by_farmer ON threads (farmer_id, updated_at DESC);
CREATE TABLE turns (
    thread_id     uuid NOT NULL REFERENCES threads (id) ON DELETE CASCADE,
    position      integer,             -- 0, 1, 2… within the thread
    message text, answer text, tools_called text[],
    requirements  jsonb,
    findings      jsonb,               -- each specialist's report, sources included
    started_at timestamptz, seconds double precision,
    UNIQUE (thread_id, position)
);
RuleWhat it protects you from
Foreign key REFERENCESA thread for a farmer who doesn't exist, or a turn for a thread that doesn't. That's why startup seeds the farmer first.
ON DELETE CASCADEOrphans. Deleting a thread deletes its turns in the same statement.
UNIQUE (thread_id, position)Two turns claiming the same place in one conversation.
Index (farmer_id, updated_at DESC)A slow sidebar. Postgres reads one farmer's threads, newest first, without scanning the table.
Transaction in record_turnHalf a save. The thread and its turn are written together or not at all.

findings stays jsonb: it's always read whole, and every specialist's report has its own shape. And the thread's turn count isn't stored at all; it's counted when you ask.

agrivibe-be/src/agrivibe/service/threads.py · record_turn (trimmed)view on GitHub ↗
async with self.pool.connection() as conn, conn.transaction():
    # create the thread on its first turn; later turns only touch updated_at
    await conn.execute("""
        INSERT INTO threads (id, farmer_id, title, created_at) VALUES (...)
        ON CONFLICT (id) DO UPDATE SET updated_at = now() ...""")
    # the turn takes the next position in its thread: 0 for the first
    await conn.execute("""
        INSERT INTO turns (thread_id, position, message, ...)
        SELECT %(thread)s, coalesce(max(position) + 1, 0), %(message)s, ...
        FROM turns WHERE thread_id = %(thread)s""")

What lives where

TableOwned byHolds
farmers, threads, turnsAgriVibeThe product data: who, which conversations, what was said and found.
checkpoints (+ blobs, writes)LangGraphThe agent's state per thread, so a conversation can continue.
storeLangGraphWhat the orchestrator remembers about the farmer.

Connecting your own database

Everything comes from one setting, DATABASE_URL in the backend's .env. The easy route is a free Neon project: create it, click Connect, copy the string4. Use the direct host, without -pooler: the checkpointer uses prepared statements, which a transaction pooler can break. A local Postgres works too, and the Docker sessions will set one up.

The chat and thread tests now run the same SQL against a real database: set TEST_DATABASE_URL to an empty one, such as postgresql://localhost/agrivibe_test. Without it, those tests are skipped.

MySQL instead? Two things would change: our SQL (small, and mostly standard), and LangGraph's saver and store, which need a version for that database. Check the persistence docs before you switch.

Check yourself

Four quick ones

Before Postgres, why did conversations vanish when you restarted fastapi dev?

In-memory data exists only while the process runs. Persisting means writing it somewhere that outlives the process.

When the checkpointer moved from memory to Postgres, what changed in the agents?

The checkpointer is injected at startup. Swap the object, keep the code. That's the point of dependency injection.

You delete a thread. What removes its turns?

turns.thread_id REFERENCES threads (id) ON DELETE CASCADE. One DELETE FROM threads, and Postgres removes the turns in the same statement.

Two messages reach one thread at the same moment. What stops both taking position 3?

The first transaction locks the thread's row until it commits, so the second waits and then takes position 4. UNIQUE (thread_id, position) is the safety net if anything slips past.

Lesson 03 · 6 minRequest flow

One message, start to finish

Your win

Trace a POST /chat request through every step, and say when the database is written.

Around 00:57 Manu wrote the whole flow as one prompt-sized paragraph. Here it is as steps:

  1. Identify the user and resolve their farmer id (on the server, lesson 04).
  2. Check the request for a thread_id. If there is one, confirm it's this farmer's and continue it. If not, make a new id.
  3. Send the message to the orchestrator. LangGraph checkpoints each step as it runs.
  4. Collect the result as a Turn: answer, tools called, requirements, findings.
  5. Record the turn: one transaction saves the thread (created on its first turn) and the turn at its next position.
  6. Return a ChatResponse: the turn plus its thread_id.
agrivibe-be/src/agrivibe/service/chatting.py · ChatService.chat (trimmed)view on GitHub ↗
if thread_id:
    await self.threads.summary(farmer_id, thread_id)  # someone else's thread is never continued
else:
    thread_id = str(uuid4())

result = await self.orchestrator.ainvoke(
    {"messages": [{"role": "user", "content": message}], "findings": {}},
    run_config("chat", thread_id, self.tracer, farmer_id),   # checkpoints go under this thread_id
    context=FarmerContext(user_id=farmer_id),
)
turn = Turn(message=message, answer=result["messages"][-1].text, ...)
await self.threads.record_turn(farmer_id, thread_id, turn)
return ChatResponse(**turn.model_dump(), thread_id=thread_id)
A question from the session

“Is the conversation kept in memory and saved to the database when the user logs out?” No. Every turn is written during the request that produced it. Nothing waits for the end. If the server dies between two questions, nothing is lost.

Look at the URL in Claude: a new chat has none; an old chat has /chat/<id>. That id is exactly the thread_id decision in step 2.

    Lesson 04 · 6 minSecurity

    Identity never comes from the frontend

    Your win

    Explain why ChatRequest has no user_id, and where real authentication would plug in.

    The old backend took a user_id in the request body. Easy, and wrong: if a browser can send its own id, anyone who learns another farmer's id can read, add or delete their data. OWASP calls this an insecure direct object reference1.

    So the new contract has no identity in it at all:

    agrivibe-be/src/agrivibe/models/chat.py
    class ChatRequest(BaseModel):
    """There is no user_id: the server decides who is asking."""
    message: str
    thread_id: str | None = None

    How a real app does it

    1. The frontend logs in with an auth service and gets a short-lived token, usually a JWT2.
    2. Every request to the backend carries the token, not an id.
    3. The backend checks the token on every request and learns the verified user id from it.

    Why every request? Tokens expire and refresh every few minutes, and a request could be forged. Checking once proves nothing about the next request.

    AgriVibe's seam: current_farmer

    AgriVibe has no auth service yet. Instead, every route that needs to know who's asking depends on one function. Today it reads the farmer from .env. Tomorrow it verifies a token, and no other code changes.

    agrivibe-be/src/agrivibe/dependencies.py · api/chat.pyview on GitHub ↗
    def current_farmer() -> Farmer:
    # Put the real authentication integration here
    settings = get_settings()
    return Farmer(id=settings.farmer_id, name=settings.farmer_name)

@router.post("/chat")
async def chat(
    request: ChatRequest,
    farmer: Annotated[Farmer, Depends(current_farmer)],       # the server decides
    service: Annotated[ChatService, Depends(get_chat_service)],
) -> ChatResponse:
    return await service.chat(request.message, farmer.id, request.thread_id)

    This is a single-tenant, white-label setup: one deployment serves one identity. Selling it to five organisations at once (multi-tenant, B2B) is when you need the full auth service.

    The same idea guards threads. If a request names a thread_id that isn't in this farmer's index, the backend answers 404, exactly as if it never existed. It never confirms that someone else's thread is there.

    Check yourself

    Think like an attacker, then like the server

    Why does ChatRequest have no user_id field?

    Whatever the browser sends, the browser controls. Identity has to be something the server owns or verifies.

    In a real app, where should current_farmer get the identity from?

    The token is issued by the auth service and checked by the backend, so the browser can't forge the id inside it.

    Why check the token on every request, not once at login?

    Short-lived tokens refresh every few minutes. Each request has to prove itself on its own.

    Primary sourceOWASP: IDOR Prevention Cheat Sheet →

    Short, concrete, and exactly the bug a user_id in the body creates.

    Lesson 05 · 5 minArchitecture

    Keep the server stateless. Make it a data problem.

    Your win

    Answer “why hit the database every time instead of keeping the thread in memory?” with the scaling argument.

    Achin asked it in the session: isn't it slow to go to the database on every message? Why not keep the conversation in memory?

    Because we're building a RESTful service, and REST's key constraint is that it's stateless: each request carries everything the server needs, and the server keeps no session between requests1. The Twelve-Factor App says the same thing about processes: stateless and share-nothing, with state in a backing service like a database2.

    The trade-off

    Keep threads in RAMKeep threads in Postgres
    Speed per readFastestA network round trip
    RestartEverything lostNothing lost
    Second serverDoesn't see the first one's threadsAny server can answer any request
    ScalingMore, bigger machines (RAM is expensive)Scale the database, which is built for fast reads and writes

    “DB scaling is easier than compute scaling.”

    Manupa, 01:09:05

    When reads do get slow, you have data tools, not compute tools: indexes, so lookups stay fast (AgriVibe's threads_by_farmer index serves the sidebar)3, then a cache such as Redis in front of the database for the latest turns4. This is the thinking behind Designing Data-Intensive Applications5, the book Manu held up.

    Aside: saved turns as training signal

    Nipuna's idea: stored turns can show where the agent went wrong. In practice, keep the raw data in the database but strip personal information (names, organisations, financial data) when you read it for evaluation or training.

    Check yourself

    Defend the design

    What does stateless mean for the AgriVibe API?

    The server keeps no session between requests. State still exists; it lives in Postgres, not in the process.

    Why push conversation state to the database rather than RAM?

    Any number of stateless servers can share one database, and databases are built for fast reads and writes.

    Reads are getting slow. What layer did Manu suggest adding next?

    A cache keeps the recent turns close, and the database stays the source of truth.

    Primary sourceFielding, ch. 5: REST · §5.1.3 Stateless →

    Where “stateless” comes from. Two paragraphs, including the trade-off you just learned.

    Lesson 07 · 6 minFrontend architecture

    Gradio is a backend for frontend

    Your win

    Explain what makes Gradio a BFF, and why AgriVibe keeps it separate from the API.

    A backend for frontend (BFF) is a server that exists for one user interface. It sits between the browser and the real services and shapes their data for that UI1.

    Runs a server?Who calls the API?
    ReactNo. JavaScript in the browser.The browser, directly.
    Next.jsYes. Server components and server functions.Either the server or the browser.
    GradioYes. Your Python runs on it.The Gradio server, in your handlers.

    In Gradio, a click in the browser triggers a Python function on the Gradio server. That function calls the API, and what it returns becomes the new state of the page. The browser never talks to the backend.

    A more precise word

    In the session we called this SSR. Strictly, Gradio doesn't send finished HTML pages. It sends new values for components, and its JavaScript frontend draws them. Call it server-driven UI: the server decides what the page shows, much like PHP or .NET MVC, which several of you knew.

    Why not put the services inside Gradio?

    Gradio runs Python, so you could import ChatService directly and skip one HTTP hop. Manu chose not to:

    • Separate scaling. Drawing pages and running LLM orchestration are different workloads. As separate processes, each can grow on its own.
    • Swappable frontend. The API is the contract. Gradio today, React or a mobile app tomorrow, with no backend change.
    • No restarts from UI edits. With the UI inside the backend, every save restarted fastapi dev.

    Why Gradio at all? The cohort works in Python, and Gradio ships a chat component with agent “thoughts” built in. A React frontend would have meant teaching React first. You're welcome to build one; Manu said he'd be proud to showcase it.

    Check yourself

    BFF in your own words

    What makes Gradio a backend for frontend rather than a plain frontend?

    Your handlers run on Gradio's server and call the API there. React has no server of its own.

    Why not move the services into Gradio and skip the API?

    It would work, but one process would do both jobs, and the API contract that lets you swap frontends would disappear.

    Primary sourceSam Newman: Backends For Frontends →

    The original write-up of the pattern, with the trade-offs. Ten minutes.

    The event pattern

    component.event(fn, inputs, outputs)1. When the event fires, Gradio reads the inputs' current values, calls fn with them on the server, and puts its return values into the outputs, in order.

    No implicit re-render

    React re-renders when state changes. Gradio doesn't. A handler must return the UI it wants. After deleting, delete_thread returns fresh(): an empty chat, no thread, a reloaded sidebar.

    Lesson 09 · 6 minAgentic engineering

    “I want the URL to be the source of truth”

    Your win

    Explain how AgriVibe keeps the open thread in the URL, and what “shaping” a codebase with an agent looks like.

    The session ended with a live change. New chats didn't change the URL; the thread id hid in the browser's session storage. Manu's prompt was one line:

    Interleaved

    Six questions, any order

    A request arrives with a thread_id from another farmer's chat. What stops it?

    ChatService.chat calls threads.summary(farmer_id, thread_id) first. It raises ThreadNotFound, and the API answers 404.

    You want each sidebar entry to show its turn count. Which file do you change?

    ThreadSummary already has turns. Only the shaping changes, in thread_choices.

    The backend restarts mid-demo. What survives?

    All of it is in Postgres, written during each request. The process holds nothing that matters.

    Where would real authentication plug in without touching other code?

    Every route depends on current_farmer. Change what it does and every route gets real identity.

    Gradio dims three components with “processing | 0.4s”. Why those three?

    Gradio shows progress on an event's outputs while it runs. AgriVibe hides it with show_progress="hidden" on fast events.

    Where does a thread's turns count in the sidebar come from?

    count(u.id) in a join of threads and turns. A stored count could drift from the real rows; a counted one can't.

    Glossary

    Thread
    One conversation: a farmer's ordered turns, under one thread_id. Avoid: session, chat log.
    Turn
    One question and everything done to answer it: answer, tools called, requirements, findings, timing. Avoid: message pair.
    ChatResponse
    A turn plus its thread_id; what POST /chat returns.
    Checkpointer
    LangGraph's saver of the graph's state at every step, keyed by thread_id. A checkpoint is one snapshot.
    Store
    LangGraph's long-term key–value storage. In AgriVibe: only the orchestrator's memory of the farmer.
    Foreign key
    A column that must match a row in another table: threads.farmer_id → farmers.id.
    Cascade
    ON DELETE CASCADE: deleting a thread deletes its turns in the same statement.
    Transaction
    Several writes that succeed or fail together, like a thread and its turn in record_turn.
    Dependency injection
    Handing an object its collaborators (store, checkpointer) instead of letting it create them.
    Seam
    One place where behaviour can be swapped without touching callers: current_farmer.
    Stateless
    The server keeps nothing between requests; state lives in Postgres.
    BFF
    Backend for frontend: a server made for one UI, between the browser and the API. Here: Gradio.
    Contract (fe)
    A pure function from backend data to what one component shows. Was: presenter.
    Handler
    What one event does: call the client, shape with contracts, return the outputs.

    The API

    POST /chatask; no id → new thread
    GET /threadslist, newest first
    GET /threads/{id}one thread + history
    DELETE /threads/{id}204
    Not yours → 404. No user_id anywhere.

    The chat loop

    1 resolve farmer (current_farmer)
2 thread_id ? check owner : uuid4()
3 orchestrator.ainvoke(...)  → checkpoints
4 Turn(...)
5 record_turn → INSERT thread + turn, one transaction
6 return ChatResponse(turn, thread_id)
